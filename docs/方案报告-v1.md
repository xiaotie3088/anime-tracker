## 1. 一句话方案

做一个**本地优先（local-first）的「当季新番抓取 + 追番管理 + 更新日历」应用**：用多个公开数据源自动汇总当季番剧清单，你勾选加入追番，日历按周/月展示每部番的更新时间与倒计时，并能导出到手机系统日历。

技术形态建议：**本地 Web 应用（后端抓取 + SQLite + 浏览器 UI）**，后期可用 Tauri 套壳成桌面程序。

## 2. 你的需求拆解

你说的问题本质是：**"当季有哪些番"和"这部番什么时候更新"这两条信息，分散在多个网站上，每次都要人工查、人工记。**

| 你的原始诉求 | 我的解读 | 设计上的落点 |
|---|---|---|
| 完整知道这一季新番的信息 | 不是"能查到"，而是"打开就知道全貌"：**数量、类型、开播时间** | 全季总览页：N 部 / 按星期分布 / 按类型分布 / 按平台分布 |
| 选择番剧加入我的追番 | 需要一个**持久化的、属于我自己的**追番列表 | 本地 SQLite（不是收藏夹/云端账号），追番列表是核心资产 |
| 在日历中显示什么时候更新 | 需要"我追的这几部，这周分别哪天几点更新" | 周视图日历 + 更新倒计时 + 变更提醒 |
| 信息从哪来 | 爬 yuc.wiki 是一种可行路径，但不是最优 | **多源融合**：官方/公开 API 为主，yuc.wiki 为补充与校对 |

我在这里加了一条你没说但一定会遇到的隐性需求：**"更新"的时间会变**（延期、改档、总集篇停更）。这一点如果不处理，日历用两周就会失真，然后你就不用了。所以本方案把「变更检测」列为核心功能而非附加功能。

## 3. 最关键的设计问题：「什么时候更新」到底指什么

这是整个项目最容易做错、也最影响体验的地方，先把它定清楚，代码才好写。

### 3.1 三个不同的"时间"

1. **日本电视台首播时间**（JST, UTC+9）——AniList / しょぼいカレンダー 这类源的强项。
2. **中国平台可看时间**（B站/爱奇艺等，UTC+8）——这才是你真正能点开看的时间，通常比日本晚数小时到一天。
3. **首播日 vs 每周更新日**——第 1 集是某天，之后每周固定星期几更新；两者不能混用一个字段。

> **已确认（v2）**：默认按**日本放送时间**展示与分组，国内平台可看时间**同时存储、作次要信息展示**。
> 注意「默认日本时间」不等于「不要国内时间」—— 两者是两个独立字段（`episode.air_at_utc` 与 `episode.pub_at_utc`）。
> 周视图的区间也因此必须用 JST 周一零点计算（`jstWeekRange()`），不能用本地时区的周一。

### 3.2 深夜番的归属问题（必须做成开关）

日本常见的 "日曜 24:30" 实际是**周一 00:30**。不同数据源会把它算到周日或周一，不同工具也会显示不一致。

- 存储层：**统一存 UTC 时间戳 + 一条 `broadcast_weekday_jst` 原始星期标记**。
- 展示层：提供开关「按日本放送日历归属 / 按我实际观看日期归属」，默认跟随你选择的基准时区。
- 绝不可以用"UTC 时间戳转本地时间再取星期"来算归属——深夜番会全错位。这是本项目第一个必须写对的工具函数。

### 3.3 需要展示的四种状态

`未开播` → `今日更新（含倒计时）` → `已更新（待观看）` → `已看完本集`，以及旁路状态 `本周停更/延期`。

## 4. 数据来源选型

### 4.1 结论先行

**建议不把 yuc.wiki 当主源，而是当作"人工校对源 + 兜底源"。** 理由：它是个人维护的静态单页站，没有 API、没有 SLA、结构可能随时变、历史上换过访问路径，一旦改版你的软件就整体失效。而它的价值（当季清单 + 国内版权平台标注）已经有更稳定的替代品。

推荐的数据源分层：

| 层级 | 用途 | 主源 |
|---|---|---|
| L1 季度清单 + 中文译名 + 国内平台链接 | "这一季有哪些番、在哪能看" | `bangumi-data` 数据集、Bangumi API |
| L2 精确放送时刻 | "具体几点几分更新" | AniList GraphQL（UTC 时间戳） |
| L3 国内真实可看时间 | "B站几点更新" | Bilibili PGC API |
| L4 交叉校验 | 修正 L1~L3 的缺失/冲突 | Jikan、yuc.wiki |
| L5 兜底 | 中文简介、海报 | TMDB、TVmaze |

### 4.2 各数据源详评

| 数据源 | 能提供什么 | 认证 | 稳定性 | 在本项目中的定位 |
|---|---|---|---|---|
| **bangumi-data**（社区维护的 JSON 数据集） | 中文/日文/英文标题、类型（tv/web/ova/movie）、放送星期与时刻、季度起止、**各平台播放页链接（B站、爱奇艺、腾讯、优酷等）**、封面 | 无需 | 高（定时构建的静态数据集） | **主力①**：季度清单 + "在哪能看" |
| **Bangumi API**（api.bgm.tv） | 条目详情、集数与分集列表、标签、制作公司、评分、封面、每日放送 `/calendar` | 无需（**必须带 User-Agent**）；同步个人收藏需 OAuth | 高 | **主力②**：元数据 + 分集 |
| **AniList GraphQL**（graphql.anilist.co） | **每集精确 UTC 时间戳**（`airingSchedule` / `nextAiringEpisode`）、格式、集数、制作、类型 | 无需（公开数据） | 高 | **主力③**：精确更新时刻 |
| **Bilibili PGC API** | 国内真实更新时间 `pub_time`、每集标题、是否会员/独家 | 无需（需 UA + Referer） | 中（有风控，需限速） | **主力④**：国内更新时间 |
| **Jikan v4**（非官方 MAL API） | 季度列表、`broadcast{day,time,timezone}`、分集、MAL ID | 无需（限速严：约 3 req/s） | 中 | 校验 / 兜底 |
| **yuc.wiki** | 人工校对的当季表格、国内平台标注、备注（延期等） | 无需 | 中低（个人站、静态页、无 API） | **补充 + 校对** |
| **TMDB** | zh-CN 简介与海报、`air_date` | API Key（免费） | 高 | 兜底 |
| **TVmaze** | `airstamp`（UTC ISO 时间） | 无需 | 中 | 兜底 |
| **Annict / しょぼいカレンダー** | 日本官方放送时刻（最权威） | Token / 接口待验证 | 中 | 高精度兜底 |

**关于 yuc.wiki 的实测要点（✅ v2 已实测，详见 [sources.md](sources.md) 第七节）**：
- 访问路径确认是 **`/YYYYMM/`**（`/202610/` = 2026年10月新番表，190KB、430 个数据行）；`/2610/` 与 `/last/` 均 404。
- 页面是**纯静态服务端渲染的表格**，无内嵌 JSON，`cheerio`/正则即可，**不需要 Selenium/Playwright**。
- **HTTPS 证书已过期（`CERT_HAS_EXPIRED`），只能走 HTTP**；站点实名「長門番堂」，挂在 Tencent EdgeOne 后面。
- 版权平台信息为**文字**（`bilibili` 等关键词命中），不是图标 —— 无需维护图标映射表。
- 额外发现：`/new/` 是「**新番卫星观测站**」（已公布未定档），可作为「即将开播」提醒的来源。
- 最有价值的是它的人工标注放送时段（如 `10/8周四深夜`、`10/4周日晚间`），
  这是解决深夜番归属歧义的权威依据，也是它值得保留为校对源的原因。
- 可参考的先例：开源项目 [AnimeGarden](https://github.com/yjl9903/AnimeGarden) 带了一个 `yuc` 抓取技能文档（含 `manual_scrape.md`）。

### 4.3 多源合并策略

每个 Provider 输出统一模型，再由 `src/core/merge.ts` 做字段级融合：

- **锚点对齐**：以 Bangumi ID 为主键，通过 `idMal`、`externalLinks`、以及标题归一化（简繁转换 + 去掉「第2季 / Season 2 / Ⅱ」等后缀 + 去括号）建立映射表。中文 B站译名 ≠ Bangumi 译名 ≠ 原名，这是必须处理的真实痛点。
- **字段级优先级**（每个字段可来自不同源）：
  - 中文标题：Bangumi > bangumi-data > yuc.wiki
  - 精确时刻：AniList > Jikan > 日本电视源
  - 国内可看时间：Bilibili > yuc.wiki > bangumi-data
  - **用户手动修正：最高优先级，永不被覆盖**
- **冲突处理**：不静默取舍，保留全部候选值并记录来源，UI 上标注「数据源存在分歧」。
- **置信度**：单源数据标记为"待确认"，两个以上源一致才标记为"已确认"。

### 4.4 抓取礼仪与缓存（必须做，否则会被封）

- 自定义 User-Agent（Bangumi 明确要求，格式如 `anime-tracker/1.0 (https://github.com/you/repo)`）。
- 全局限速：同一域名 ≥1 秒/请求；Bilibili 更保守。
- **原始快照落盘**：每次抓取的原始 JSON/HTML 存 `data/snapshots/{source}/{timestamp}.{ext}`，好处有三：可回溯、可离线复现解析逻辑、**通过对比快照自动发现"延期/改档"**。
- 失败降级：单源失败不阻塞整体，用其他源补齐并标记缺失字段。

## 5. 数据模型（草案）

```sql
-- 番剧主表（锚点：bgm_id）
subject(
  id INTEGER PRIMARY KEY,        -- 自增内部 ID
  bgm_id INTEGER UNIQUE,         -- Bangumi ID（主锚点）
  anilist_id INTEGER, mal_id INTEGER, bili_season_id INTEGER,
  title_cn TEXT, title_original TEXT, title_en TEXT,
  aliases TEXT,                  -- JSON 数组，用于搜索
  cover_url TEXT, banner_url TEXT,
  media_type TEXT,               -- TV / WEB / OVA / MOVIE
  total_eps INTEGER, duration_min INTEGER,
  studios TEXT, genres TEXT,     -- JSON 数组
  season TEXT,                   -- "2026-10"
  first_air_at TEXT,             -- ISO8601 UTC，首播
  broadcast_weekday_jst INTEGER, -- 0-6，日本放送日历归属（关键字段）
  broadcast_time_jst TEXT,       -- "24:30"
  status TEXT                    -- 未开播 / 放送中 / 完结
);

-- 分集表
episode(
  id INTEGER PRIMARY KEY,
  subject_id INTEGER, ep_number REAL,   -- REAL 以支持 5.5 话
  title TEXT, title_cn TEXT,
  air_at_utc TEXT,        -- 日本放送精确时刻
  pub_at_utc TEXT,        -- 国内平台可看时刻
  duration_min INTEGER,
  UNIQUE(subject_id, ep_number)
);

-- 原始抓取快照（用于变更检测与离线复现）
source_record(
  id INTEGER PRIMARY KEY, source TEXT, url TEXT,
  fetched_at TEXT, content_hash TEXT, payload_path TEXT
);

-- 我的追番（核心资产）
my_anime(
  subject_id INTEGER PRIMARY KEY,
  state TEXT,             -- 在看 / 想看 / 弃番 / 看完
  watched_eps REAL DEFAULT 0,
  notify_enabled INTEGER DEFAULT 1,
  added_at TEXT, note TEXT
);

-- 用户手动修正（最高优先级）
schedule_override(
  id INTEGER PRIMARY KEY,
  subject_id INTEGER, ep_number REAL,
  air_at_utc TEXT, pub_at_utc TEXT, reason TEXT
);

-- 变更历史（延期提醒的数据基础）
change_log(
  id INTEGER PRIMARY KEY, subject_id INTEGER, ep_number REAL,
  field TEXT, old_value TEXT, new_value TEXT, detected_at TEXT
);
```

**为什么是 SQLite 而不是 JSON 文件**：追番列表会长期积累、要跨季度查询、要做"我上一季追了哪些没看完"，SQLite 零配置、单文件、可备份，且是本地优先方案的标准答案。

## 6. 功能清单

### 6.1 核心功能（P0，不做就不成立）

| 功能 | 说明 |
|---|---|
| 当季全番抓取与汇总 | 一条命令/一个按钮，拉取当季全部番剧，多源合并去重 |
| 全季总览页 | 数量统计、按星期分布、按类型/平台筛选、搜索（支持中文名/原名/别名） |
| 追番管理 | 加入/移除、状态标记（在看/想看/弃番）、观看进度（追到第几集） |
| 周视图日历 | 一周七天，我追的番按更新时间落格，显示集数、平台、倒计时 |
| 今日/即将更新列表 | "今天还有什么要更新"、倒计时排序 |
| 数据源标注 | 每个时间点标明来源，分歧时提示 |
| 手动修正时间 | 源不可靠时的兜底，永不被覆盖 |
| 本地持久化 + 导入导出 | 追番列表属于你，可备份、可迁移 |

### 6.2 我建议加的功能（已站在你的角度评估）

**✅ 强烈建议采纳（性价比高）**

1. **`.ics` 日历订阅导出** —— 生成的日历文件可导入手机系统日历/Google 日历，不用打开这个软件就能在手机上看到更新时间。实现成本极低、收益极高，是"手机上看得到"的最省事方案。
2. **更新倒数计时 + 桌面通知** —— 追番党最直接的爽点；通知必须可关闭、可按番单独开关。
3. **延期/改档变更检测与提醒** —— 通过快照对比实现。它真正解决"我以为今晚更新，结果停更了"这个反复出现的痛点，是留住用户的关键。
4. **全季视图里的"即将开播"提醒** —— 新番第 1 集时间往往集中在季初几天，容易漏；单独聚合一份"未来 7 天开播清单"。
5. **别名统一搜索** —— B站译名、Bangumi 译名、日文原名三者不一致是高频摩擦点，搜索必须三路通吃。
6. **月视图** —— 看整季的时间分布（哪几周扎堆、哪周空），用来决定"这季我要追几部"。
7. **离线可用** —— 抓取结果缓存本地，断网也能看日历。

**⚠️ 可选，看你是否觉得有用**

8. **一键同步追番到 Bangumi 收藏**（OAuth）—— 如果你本来就重度使用 Bangumi，这能省一次手动录入；否则是纯负担，建议延后。
9. **按平台筛选（只看 B站 / 只看我订阅的平台）** —— 如果你基本只在 B站看，那它就是主筛选器；如果你多平台混看，价值一般。
10. **局域网/手机浏览器访问** —— 睡前躺床上看明天更新什么。用响应式网页即可，不必做原生 App。
11. **季度归档与"我追番的历史统计"** —— 好看但不刚需，容易变成做完就没人看的功能。
12. **番剧中文简介**（TMDB/AniList）—— 你追番时大概已经看过 PV 和简介了，属于锦上添花。

**❌ 不建议做（明确排除）**

- **在线播放 / 下载 / 弹幕**：版权风险 + 工程量巨大，且 B站 已经做得比你好。
- **AI 推荐 / 评分排行榜**：你的痛点是"信息不全"，不是"不知道看什么"；排行榜类需求去 Bangumi/豆瓣即可。
- **社交、评论、分享、多人协作**：单人工具没有收益，只会增加复杂度。
- **账号系统 + 云服务器同步**：运维成本高；本地文件 + 网盘/OneDrive 同步就能达到同样效果。
- **独立原生手机 App**：先用响应式 Web + `.ics` 导出覆盖 90% 的手机场景，等确认自己天天用之后再说。

## 8. 技术选型

### 8.1 三种形态对比

| | A. 本地 Web 应用（推荐） | B. 纯静态 PWA + 云端定时抓取 | C. Tauri 桌面应用 |
|---|---|---|---|
| 构成 | 后端抓取 + SQLite + 浏览器 UI | GitHub Actions 定时抓取 → 静态 JSON + 前端 | Tauri 打包前后端 |
| 开发速度 | **最快**，调试最方便 | 快，但状态在浏览器 | 慢，打包/签名/更新链路长 |
| 追番数据 | SQLite 单文件，好备份 | localStorage，换设备麻烦 | SQLite，好备份 |
| 手机可用 | 局域网可访问 | **天然可用** | 需额外方案 |
| 通知/自启 | 需自己实现（或托盘） | 依赖浏览器/邮件 | **最自然** |
| 运维成本 | 要保证服务在跑 | **零成本** | 中 |
| 适用 | 主要在自己电脑上用 | 想要零服务器 + 手机为主 | 想做成正式桌面软件 |

**我的建议：走 A，但把抓取层与 UI 完全解耦。**
理由：A 的开发/调试成本最低，且因为抓取层是独立模块，将来想转成 C（Tauri 套壳）或 B（把抓取结果导出为静态 JSON）都不需要重写核心逻辑。先用 A 跑通，等你确认自己天天用，再决定要不要打包。

### 8.2 推荐技术栈

- **语言：TypeScript 全栈**。理由：Node v24 与 pnpm 你本机已有；抓取层与前端共享类型定义（`SeasonAnime` 等模型只写一次）；日历与 UI 生态成熟。
  - 若你更熟悉 Python，等价方案是 `httpx + selectolax + FastAPI + SQLite`，抓取部分甚至更顺手 —— 但类型共享要额外维护。**这个选择权在你（见第 10 节）。**
- **后端**：Fastify（或 Hono）+ `better-sqlite3`
- **抓取**：`undici`/`fetch` + `cheerio`（HTML 解析，用于 yuc.wiki）+ `zod`（响应校验，防止源改版后静默写脏数据）
- **定时任务**：`node-cron`（每日同步一次 + 每 6 小时检查变更）
- **前端**：React + Vite + Tailwind CSS；日历可自写（周视图逻辑简单，自写更可控）或先用 FullCalendar 快速起量
- **打包**：pnpm workspace 单仓多包

### 8.3 目录结构（v2 已按实际实现更正）

```
anime-tracker/
├─ src/
│  ├─ core/            # 零依赖纯逻辑：time(时间/深夜番) / calendar(日历分组)
│  │                   #   backlog(补番规则) / types / merge(多源融合)
│  ├─ providers/       # http(代理+限速) / snapshot(快照) / validate(zod 友好报错)
│  │                   #   bangumi-data / anilist / provider(统一接口)
│  └─ server/          # db(node:sqlite) / schema.sql / cli.ts
├─ scripts/
│  ├─ verify.ts        # 离线自检（零依赖、单进程）
│  ├─ probe-sources.ts # Phase 0 数据源探测（零依赖）
│  └─ diagnose-network.ts
├─ data/               # anime.db + snapshots/ + cache/（已 gitignore）
└─ docs/
   ├─ 方案报告-v1.md    # 本文件
   ├─ sources.md        # ★ Phase 0 实测结论
   └─ 决策记录.md        # ★ ADR：为什么这么做
```

**与 v1 的差异及原因**：原计划用 pnpm monorepo（`apps/` + `packages/`）。
实际改为**单包 + 相对 `.ts` 导入**，因为 Node 24 原生支持类型擦除，
`node src/server/cli.ts` 可直接运行，跨包名解析只会增加负担而无收益。
将来加 Web UI 时再单独给前端建包。详见 [决策记录.md](决策记录.md) T1。

### 8.4 Provider 统一接口（关键抽象）

```ts
export interface Provider {
  id: string;
  /** 该源是否负责"季度清单" */
  providesSeason?: boolean;
  fetchSeason(year: number, month: 1 | 4 | 7 | 10): Promise<RawSeasonAnime[]>;
  fetchEpisodes?(externalId: string): Promise<RawEpisode[]>;
  /** 补全单部番的字段 */
  enrich?(anime: RawSeasonAnime): Promise<Partial<RawSeasonAnime>>;
}
```

新增/替换数据源 = 新增一个文件，不改动其他代码。这是应对"源站改版"的唯一有效手段。

## 9. 分阶段路线图

- Bangumi 收藏 OAuth 同步（如需要）。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 源站改版 / 加反爬 | 抓取直接失效 | Provider 插件化 + zod 校验早失败 + 多源互备 + 快照可复现 |
| AniList 对当季番 `airingSchedule` 覆盖不全 | 精确时刻缺失 | 降级到 Jikan `broadcast` + 用户手动修正 |
| Bilibili 风控 | 拿不到国内时间 | 限速 + 缓存 + 只在必要时请求 + 手动兜底 |
| 深夜番/时区处理错误 | 整个日历错位一天 | 统一存 UTC + 保留 JST 星期标记 + 单元测试覆盖 24:00~25:59 边界 |
| 多源标题不一致 | 重复条目 / 匹配失败 | 多 ID 锚定（bgm/anilist/mal/bili）+ 归一化 + 人工合并入口 |
| 版权 | 法律风险 | 只存元数据与链接，不存视频、不存图床盗链以外的内容 |
| 自己做的东西自己不用 | 白干 | Phase 1 就产出可用的 CLI，Phase 2 后立刻接入日常使用 |
