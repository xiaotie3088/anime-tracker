# 决策记录（ADR）

记录「为什么这么做」。每条都写清背景、结论、理由，以及**被否决的替代方案** ——
后者是为了未来的你（或未来的我）不会再纠结一遍。

- 建立日期：2026-10-02
- 状态：D1–D6 由你确认；T1–T13 为技术决策，理由与实测依据一并记录；
  D7–D12 为第二轮（用户提出 5 个诉求那轮）的决策

## D1 · 技术栈：TypeScript 全栈

- **决定**：TypeScript 全栈，Node 24 运行时，pnpm 管理依赖。
- **理由**：抓取层与前端共享同一套类型定义（`Subject` / `Episode` 只写一次）；
  本机已有 Node 24 与 pnpm；日历与 UI 生态成熟。
- **否决**：Python 后端（抓取写起来更顺手，但类型要维护两份）。

## D2 · 「更新」的默认含义：日本放送时间

- **决定**：默认按**日本放送时间（JST）**展示与分组；国内平台可看时间同时存储、作为次要信息展示。
- **理由**：你选择了以日本放送日历为准。这样周视图的边界就是 JST 周一零点，语义统一。
- **影响**：
  - 周视图区间必须用 `jstWeekRange()` 算，不能用本地时区的周一。
  - 国内时间不能丢 —— 数据模型里 `episode.pub_at_utc` 与 `air_at_utc` 是两个独立字段。
  - 深夜番的两种归属口径仍然都要保留（见 T5）。
- **注意**：「默认显示日本时间」**不等于**「取消国内时间」。两者是并存的，只是默认口径不同。

## D3 · 形态：本地 Web，单机使用

- **决定**：后端抓取 + SQLite + 浏览器 UI，只在本机跑；不做账号、不做云同步。
- **理由**：只在自己电脑上用，开发与调试成本最低；追番数据是本地文件，好备份。
- **影响**：
  - 不需要登录、权限、多用户、并发控制。
  - 不需要部署与运维。
  - 手机端后续用 `.ics` 导出覆盖（Phase 3），而不是做原生 App。

## D4 · 数据源策略：多源融合，yuc.wiki 降为校对源

- **决定**：以 bangumi-data + AniList + Bilibili 为主力，Jikan 兜底，yuc.wiki 作校对源。
- **实测支撑（见 [sources.md](sources.md)）**：
  - bangumi-data 当季覆盖率：中文名 95%、放送时刻 100%，且带跨源 ID 锚点。
  - AniList 每集精确时刻覆盖 94%，但**没有中文名**。
  - 两者在「精确时刻」上正好互补 —— 这是多源设计最直接的收益。
  - yuc.wiki 的 HTTPS 证书已过期、无 API、单一维护者、页面里混着手办广告表格。
    它的人工标注质量很高，但**不适合承担主干数据**。
- **否决**：以 yuc.wiki 为主源（稳定性不足，会拖垮整个软件）。

## D5 · 不做 Bangumi 账号同步（OAuth）

- **决定**：不接入 Bangumi OAuth，不读写你的 Bangumi 收藏。
- **理由**：你不需要；省掉一整套 token 管理、刷新、失效处理。

## D6 · 新增「补番库」类别

- **来源**：你提出的需求 —— 「番剧没看完但到下一个季度了」。
- **决定**：
  - `my_anime.category` 增加 `backlog`（另有 `tracking` / `finished` / `dropped`）。
  - 季度同步时**自动归档**：`已播完 + 看了 ≥1 集 + 没看完` → 补番库。
  - 支持手动加入**任意老番**（所以 `add` 必须支持搜索，而这又倒逼出「按中文名搜索」的需求）。
  - 显示剩余集数与预估时长。
  - **默认不进日历**：老番没有「更新时间」，硬塞进日历会污染「今天更新什么」这个核心语义。
    提供可选的补番计划（每周几看 / 每天几集），开启后才出现在日历上。
- **刻意不做的自动行为**：
  - 一集都没看的不自动迁移（那是「想看」，不是「没看完」）。
  - 总集数未知的不自动迁移（不能靠猜）。

## T1 · 单包结构 + 相对 `.ts` 导入 + Node 原生跑 TypeScript

- **决定**：不用 pnpm monorepo 的 `packages/*` 布局，改为单包 `src/{core,providers,server}`，
  内部一律用带 `.ts` 扩展名的相对导入；不引入构建步骤。
- **理由**：
  - Node 24 原生支持类型擦除，`node src/server/cli.ts` 直接运行。
  - 跨包名导入会牵扯 workspace 解析与 exports 映射，对一个单人本地工具是净负担。
  - 结果：`pnpm install` 之后没有任何 build 步骤，改完代码立刻能跑。
- **代价**：将来加 Web UI 时要单独给前端建包（Vite 自己处理打包，不受影响）。
- **约束**：因为要「可擦除」，代码里不能使用 `enum`、`namespace`、构造函数参数属性。
  tsconfig 里开着 `erasableSyntaxOnly` 来强制这一点。

## T2 · 用 `node:sqlite` 而不是 better-sqlite3

- **理由**：better-sqlite3 是原生模块，Windows 上装 node-gyp 是常见坑；
  `node:sqlite` 是 Node 24 内置，**零依赖**。
- **正面副作用**：`scripts/verify.ts` 可以在**一个包都没装**的情况下跑起来。
- **代价**：`node:sqlite` 仍是实验特性，启动会打印一条 `ExperimentalWarning`，可忽略。
- **注意**：它只接受 `null | number | string | bigint | Uint8Array`，
  布尔与 `undefined` 必须显式转换（见 `db.ts` 的 `bind()`）。

## T3 · 用 undici 而不是全局 fetch

- **理由**：全局 fetch **不读 `HTTPS_PROXY`**，而实测 `api.bgm.tv` 的 DNS 被污染到 Facebook 网段，
  国内想用 Bangumi 基本都得走代理 —— 这是硬需求，不是可选优化。
- **附带能力**：可以对单个域名放宽 TLS 校验（`allowInsecureTls`），
  用于证书已过期的 yuc.wiki，而**不会全局关闭证书校验**。
- **实测依据**：见 [sources.md](sources.md) 第六、七节。

## T4 · TypeScript 用 5.9 而不是 7.x

- **原因**：TS 7（原生版）需要平台二进制包 `@typescript/typescript-win32-x64`，
  当前镜像装不上，`tsc` 直接报 `Unable to resolve`。
- **决定**：锁 `^5.9.0`（纯 JS，跨平台无坑），并且它已支持 `erasableSyntaxOnly`。
- **何时可以再考虑 7.x**：等平台包在所有镜像上齐了。

## T5 · 时间统一存 UTC，并保留两个星期归属

- **决定**：所有时刻以 ISO 8601 UTC 存储；`subject` 上另存 `broadcast_weekday_jst`（放送日历）
  与 `broadcast_time_jst`（字面写法，如 `"24:30"`）。
- **理由**：这是本项目最容易错的地方。「日曜 24:30」的放送日历归属是周日、真实钟点是周一。
  两种口径都有用，所以都存，由 UI 开关决定用哪个。
- **禁止**：用「UTC 转本地再取星期」来算归属 —— 深夜番会整体错位一天。
- **反推函数**：`toLiteralJstTime()` 能从 UTC 时刻还原出 `"24:00"` 这种字面写法
  （依据：JST 凌晨 0–6 点播出的番在日本排期表上属于前一天），并且与 `resolveAiringSlot()` 互为逆运算（有自检覆盖）。
- **时区实现**：刻意不使用 `Intl` / 时区数据库，只用固定 UTC 偏移做算术 ——
  避免 small-icu 环境抛错，也保证结果完全确定、可测试。

## T6 · 原始响应落盘为快照

- **决定**：每次抓取的原始响应存 `data/snapshots/`（探测脚本存 `data/probe-*/`）。
- **收益**：
  1. 解析逻辑写错时可以**离线重放**，不用再打源站。
  2. 新旧快照 diff 出「延期 / 改档」—— 这是延期提醒的数据基础。
  3. 调试期间反复跑解析不触发限速。
- **实际收益案例**：本次接入 bangumi-data 时，schema 因 `sites[].id` 可能缺失而报错，
  直接用已保存的 7.8MB 快照离线定位，没有重新下载。

## T7 · 自检脚本用单进程零依赖写法，不用 node:test / vitest

- **原因（实测）**：`node --test` 会 spawn 子进程走管道，在受限沙箱/环境中直接 `EPERM` 失败。
- **决定**：`scripts/verify.ts` 自己写极简断言骨架，单进程运行（`node:assert/strict`），
  并且只依赖 Node 内置模块 —— 因此**不需要 `pnpm install` 就能验证核心逻辑**。
- **代价**：没有测试夹具、mock、覆盖率报告。对当前规模（49 项检查）不值得引入。

## T8 · 补番库默认不进日历

- **理由**：日历的语义是「今天有什么更新」。老番不会更新，塞进去会稀释这个语义。
- **决定**：默认纯待看清单 + 进度记录；提供**每部独立**的可选计划
  （`planned_weekday_jst` / `planned_eps_per_day`），开启后才生成「今日补番任务」。

## T9 · `add` 优先复用本地已落库的富记录

- **背景（dogfooding 发现的真问题）**：
  用搜索添加一部番时，拿到的是**单一数据源**的记录（AniList 没有中文名）；
  而季度同步落库的是**多源融合后的富记录**。
  不查重就会出现同一部番两份记录 —— 一份有中文名、一份没有。
- **决定**：`add` 先用 `findSubjectByExternalId()`（bgm/anilist/mal ID）查库；
  命中则**直接复用其 key**，不覆盖已有的富数据。
- **附带**：`search` 默认先搜本地库（中文名/原名/别名都参与匹配），
  这样「B站译名 / Bangumi 译名 / 日文原名」打哪个都能搜到。

## D7 · yuc.wiki 以「校对源」的形态接入，且走 HTTP

- **决定**：作为第 3 个 Provider 接入，但**只取它在别处拿不到的东西**：
  字面放送时刻（`25:00` 这种写法）、放送日历归属、制作公司、中文/日文标题。
- **为什么它在这个位置上最有用**（实测支撑见 [sources.md](sources.md) 第七节）：
  - 它的按天网格直接给 `imgtext4 = "25:00"` —— 这正是「放送日历 vs 真实钟点」歧义的
    原始表述，不需要像 bangumi-data 那样用「凌晨 0-6 点算前一天」的惯例反推。
  - 它带日文原名，这是跨源匹配的钥匙；80 条里有 69 条有原名。
- **走 HTTP 而不是 HTTPS**：站点证书已过期（`CERT_HAS_EXPIRED`）。
  `http.ts` 里保留了按域名放宽 TLS 的能力，但这里连放宽都不需要，直接用 `http://` 更简单。
- **解析器要「响亮地失败」**：解析结果少于 20 条就抛错。源站改版时必须立刻暴露，
  否则会静默变成「这季没番」，而这类错误在界面上看起来和「真的没番」一模一样。

## T10 · 延期检测的核心是「别报假警」，不是「能对比」

- **决定**：`server/changes.ts` 里加两道过滤，宁可漏报也不误报：
  1. **源优先级过滤**：只有当新值来自同一个源、或来自优先级更高的源时才算变更。
     否则某个源一次超时，字段落到更弱的源上，就会产生一条假延期。
  2. **最小时间差**：默认忽略小于 60 秒的差异。
- **新增分集要聚合**：`airingSchedule` 会随季度推进逐步补全，
  一次同步冒出 11 集「新增」并不是改档。所以聚合成一条「新增 3 集排期（第 5~7 话）」。
- **顺序不能反**：必须在写库**之前**比对，写完之后旧值就不存在了。
- **验证方式**：除单元测试外，还加了一条接口级测试 ——
  **连续两次同步，第二次必须产生 0 条变更**。这是能真正证明「不会天天弹假警报」的测试。

## T11 · 桌面端不用 Electron / Tauri

- **决定**：用一个 `.vbs` 启动器 + 桌面快捷方式：后台静默拉起服务，等 `/api/health`
  真的响应后再打开浏览器。
- **理由**：打包成 exe 需要引入 Rust（Tauri）或几百 MB 运行时（Electron），
  还要处理打包、签名、更新链路，而换来的唯一好处是「目标机器不用装 Node」——
  而本机已经有 Node。
- **收益**：双击即用、启动 1~2 秒、零构建步骤、改代码立刻生效（不用重新打包）。
- **代价（明说）**：不是单文件 exe，依赖项目目录里的 Node 环境。
- **已处理的细节**：服务已在跑时不重复启动；浏览器打开失败时依次退化为
  `shell.Run url` → `cmd /c start` → `rundll32 url.dll,FileProtocolHandler`，
  全失败则弹框告知手动访问地址。

## T12 · `desktop/` 下的启动脚本必须纯 ASCII（含注释）

- **背景**：这个坑踩了三次，每次都表现成完全不同的错误：
  - `.vbs` 是 UTF-8 → WSH 按 ANSI 读 → 直接报「未结束的字符串常量」。
  - `.ps1` 是 UTF-8 无 BOM → PowerShell 5.1 按 GBK 读 → 更隐蔽：
    **某行注释以中文结尾时，末尾字节被当作 GBK 前导字节吞掉换行，
    导致下一行代码被并进注释里**，表现为莫名其妙的「参数为空字符串」。
  - `.cmd` 里有中文 `echo` → cmd.exe 按 OEM 代码页解析 → 把中文当成命令报错。
- **决定**：三个脚本全部纯 ASCII；中文（快捷方式名）用 Unicode 码点拼出来。
  **界面与文档不受影响，照常用中文。**
- **为什么不用 BOM 解决**：BOM 会被多数编辑器和任何"重存为 UTF-8"的工具静默丢掉，
  问题会复发；ASCII 不会坏。
- **顺带**：启动器脚本的文件名也改成 ASCII（`start-anime-calendar.vbs` 等），
  减少一处需要转义的地方；文件名本身用中文是安全的（NTFS 存 UTF-16），
  出问题的只有**文件内容**的编码。

## T13 · 前端用原生 ES 模块，不引 React / Vite

- **决定**：`web/` 下三个文件（`index.html` / `styles.css` / `app.js`），
  自己写一个 `state` + 每个视图一个渲染函数 + 事件委托。
- **理由**：界面只有 5 个视图；引入框架会带来构建步骤和几百个依赖，
  而收益（组件复用）在这个规模下不明显。保持「装完依赖就能跑、没有构建步骤」这个特性。
- **代价**：没有组件化、没有类型检查（`app.js` 只是 `.js`）；靠 `node --check web/app.js`
  做语法检查，靠 `scripts/verify-api.ts` 保证接口契约不被改坏。

## D8 · 临时机翻译名：两态出处 + 官方名永远覆盖 + 不进 fieldSources

- **背景（你的诉求 3）**：「有些番没中文译名，能否对原名机翻，加『临时机翻译名』；
  官方译名出来后一键更新改成官方名」。
- **决定**：
  1. `subject` 加两列：`title_cn_source`（`'official'` / `'machine'`）与 `title_cn_source_at`（机翻时刻）。
     **NULL 一律视为 official** —— 这样引入这两列之前落库的历史数据零迁移就语义正确。
  2. 官方中文名**永远覆盖**机翻名，并把出处改回 `'official'`、清掉机翻时刻。
  3. 机翻名**不进 `fieldSources`**。那个字段是「官方源的字段级出处」，
     机翻名写进去就等于把自己伪装成官方来源。改为在详情卡单独标出处。
  4. 机翻名只写 `title_cn`，同时把**原名与英文名并入 `aliases`** ——
     否则机翻名一写进来，用原名就搜不到这部番了。
  5. `SOURCE_IDS` 增加 `'mt'`，标签「机器翻译（临时）」，用于来源展示。
- **不该翻的三种情况**（有自检覆盖）：
  - 已有官方中文名的（翻了也会被覆盖，白翻）；
  - 原名本身已是**可读中文**（有汉字且无假名）：`夏日` / `魔法使之夜`；
  - 原名是**纯拉丁字母**：`DARK MACHINE THE ANIMATION` 机翻成「黑暗机器 动画」反而是**信息损失**。
  - 边界：只要有假名就必须翻 —— `装甲騎兵ボトムズ 灰色の魔女` 含片假名，是日文，该翻。
- **供应商选择**（实测，别重测）：Google 系全不可达、`edge.microsoft.com/translate/auth` 已下线（404）、
  `api.cognitive.microsofttranslator.com` 需订阅密钥（405）；
  **`cn.bing.com` 的 token 方案可用且质量最好**，MyMemory 兜底。
  token 要抓一个 **627KB** 的页面、有效期约 1 小时，所以**进程内缓存复用**，一次会话翻一批。
- **质量定位**：专有名词会错（`マゼンチュ` → 「马森楚」），其余相当可读。
  所以它是「临时译名」，这正是「标记 + 自动替换」机制存在的理由。

## D9 · 历史季度保留：默认不回填全部，回填最近 N 季且增量

- **背景（你的诉求 4）**：「这个季度过去之后还会不会保留之前的番剧信息」。
- **先澄清事实**：数据库层面**本来就保留**。`subject` / `episode` 按 `season` 存，
  同步只 upsert 当季，**从不删除**任何历史季度；`availableSeasons()` 与界面下拉框也一直支持切换。
- **真正缺的是什么**：没人替你把历史季度**抓下来** —— 同步只抓界面选中的那一季，
  所以 2026-07 及更早的数据库里根本没有。
- **决定**：
  - 新增 `syncArchive(db, { fromSeason|toSeason|backfill|force })`，按季度循环抓取。
  - **默认只回填最近 3 季**（`--backfill=N` 可调）。不做「从 2020 年起全抓」：
    那既慢又容易触发限速，而且老季度的 yuc.wiki 页面多半 404。
  - **增量**：已有数据的季度跳过（`seasonSubjectCount` 判定），`force` 才重抓。
  - **容忍失败**：每个季度单独 try/catch，老季度抓不到属正常，如实报告状态
    （`fetched` / `skipped` / `empty` / `failed`），不中断整体。
  - **季度间留 1 秒间隔**，别把源站打爆。
  - 界面把「库里有哪些季度、各多少部、最后更新时刻」摊开说明，让「保留」这件事**可见**。

  - **季度归属只由数据自身决定，不由写入顺序决定**（这一条是被回归逼出来的）：
    归属取「**集数最小的那一集的放送时刻**」推出的季度。
    - 不能用「落在哪个加宽窗口」判：加宽 7 天后 2026-07 的区间会覆盖到 10-07，
      把 10 月新番判给 7 月。
    - 不能用「谁最后写入」判：先写当季、后回填旧季，交叠的条目就会被判给旧季
      （实测当季从 123 部掉到 56 部）。跨季连续放送的番本来就同时出现在两季的清单里。
    - 不能用 `firstAirAtUtc` 优先：它在不同源的清单里时有时无，
      会让「写入时判定」与「写库后纠正」算出不同结果，归属来回抖动并刷出假变更。
    - 实现只有一份（`db.ts` 的 `deriveSeasonFromAirTimes`）：
      写入时由 `resolveSeasonForWrite` 用，写库后由 `repairSeasonAssignments` 用，
      所以两者必然一致、**幂等**。改其中一处必须同时改另一处。
  - **搜索导入也要回填季度**：抓取时季度由调用方指定，但搜索导入没有这个上下文。
    以前一律写 `season = null`，于是从搜索加入的番在全季总览里**永远看不到**
    （总览按 `WHERE season = ?` 过滤），只能在「我的追番」里找到 ——
    用户会以为「加进去的番没了」。现在 `RawSeasonAnime` 带可选的 `season`，
    AniList 的 `season`/`seasonYear` 会被翻成本项目的季度 ID，导入时写进去。

## D10 · 追番列表是资产：写库前自动备份 + 可导出

- **背景（你的诉求 5）**：追番数据不可重建，而实测发现了一条**真实的数据丢失路径**。
- **实测到的真实陷阱（这条最重要）**：
  本项目用 WAL 日志模式，**只拷 `anime.db` 会得到不完整的库**。
  实测：只拷主文件时 `subject` 有 126 行，而 `my_anime` **是 0 行** —— 追番列表整条丢。
  也就是说，任何「直接复制数据库文件」的备份/同步方式都会静默丢用户数据。
- **决定**：
  1. 备份顺序必须是：先 `PRAGMA wal_checkpoint(TRUNCATE)` 合并 WAL，再拷 `anime.db`，
     并且**把 `-wal` / `-shm` 也一起拷**（checkpoint 失败时的第二道保险）。
  2. 触发时机：**启动服务时** + **每次写库之前**（同步 / 一键更新）。
  3. 保留策略：只留最近 **20** 份（`pruneBackups`）。备份不能无限增长，
     但也不能只留一份 —— 一份被误删就没了。
  4. 新增 `GET /api/export` + 界面「导出我的数据」按钮：导出追番列表与进度、
     手动修正、变更历史，并带上番剧名这类人类可读信息（导出的东西要能看懂）。
  5. `node src/server/cli.ts backups` 让备份可见。
- **附带**：`runFullUpdate` 在**任何写库之前**先备份，所以「更新数据」失败也不会让数据更差。

## D11 · 自动归档必须「可见」——沉默的搬运就是「记录消失」

- **背景（你的诉求 5）**：「每次进入项目，上次更改的记录都会消失」。
- **排查结论**：不存在「Web 界面误清数据」的路径（`my_anime` / `schedule_override` 只被 CLI 的
  `reset` 清空，`server.ts` 里没有任何接口能清空它们；同步只 upsert，从不 DELETE）。
  真正的观感来源是**自动归档**：`已播完 + 看了 ≥1 集 + 没看完` 的追番会被移进补番库，
  于是它在「追番中」里消失了。
- **决定**：行为本身是 D6/T8 明确要的、**不能删**，但必须让它可见：
  - `autoArchiveFinished` 返回 `moved: [{ key, title, to }]`，**带番名**
    （只给内部 key 用户看不懂，等于没说）。
  - 同步/更新的返回里带上 `moved`，界面 toast 说出「哪几部被移到了哪里」，
    更新明细面板里再列一次。
  - 「我的追番」页顶部说明这个规则，并强调「一集没看的不动」。
- **顺带修掉的两个观感问题**：
  - 搜索导入的番 `season = NULL`，全季总览按 `season = ?` 过滤，所以它只在「我的追番」里可见 ——
    在总览页找就会觉得「没了」。界面已明确标注季度与「库里没有」的状态。
  - 机翻名被同步覆盖成 official（见 D8）会让「临时机翻」标记消失，这本身也是一种「记录消失」。

## D12 · 桌面启动器加固：诊断日志 + 调试入口 + 不破坏已有快捷方式

- **背景（你的诉求 1）**：桌面快捷方式「不能用」。
  上一轮实测过 `.vbs` 单独运行是**成功**的，所以坏的不是逻辑，而是**运行时环境或触发方式**
  （杀软拦截 VBS / OneDrive 桌面同步卡住 / node 不在 PATH）。
- **决定**：
  1. `.vbs` 每一步都写进 `data/launcher.log`（找 node、起服务、探健康、开浏览器），
     静默失败时也能看到原因。日志失败绝不影响启动（所有文件操作都吞异常）。
  2. 不再依赖 `cmd /c node.exe` 走 PATH：直接探测
     `%ProgramFiles%\nodejs` / `%ProgramFiles(x86)%\nodejs` / `%LOCALAPPDATA%\Programs\nodejs`，
     全部失败才退回 `where node`（并把这次降级记进日志）。
  3. 新增**不依赖 WSH** 的 `desktop\start-anime-calendar-debug.cmd`：
     可见控制台、真实错误输出、`pause` 住不闪退。杀软拦 .vbs 时这是唯一入口。
  4. `create-shortcuts.ps1` 创建**两个**入口：「新番追番日历」（静默 VBS）与
     「新番追番日历调试」（可见 CMD）。
  5. **写权限预检**：创建任何快捷方式之前先写一个探测文件。
     起因是加固过程中发现的真问题 —— 没有预检时，脚本会先删掉旧快捷方式、
     然后才因为桌面不可写而失败，**结果是三个快捷方式全丢**。
     「会破坏被验证对象的验证步骤」比没有验证更糟。
  6. `desktop/*` 继续**纯 ASCII**（T12）。用户可见的中文消息由 Unicode 码点用 `ChrW` 拼出来。
  7. **不依赖 http 网址关联**（后来实测发现的真问题）。这台机器的默认浏览器是夸克，
     而它的 exe 已被移走：
     `HKCU\...\UrlAssociations\http\UserChoice` = `QuarkHTM` →
     `"D:\Program\Quark\quark.exe"`（文件不存在）。
     于是**任何**「打开这个网址」的调用都弹「找不到应用程序」。
     所以启动器改为**直接调用浏览器 exe**：先按注册表里的 `UserChoice` 找出用户选的浏览器
     并直接启动它（尊重用户选择，但 exe 不存在就跳过），再依次尝试
     Chrome / Edge / Firefox 的常见路径。实测日志见 `desktop/README.md`。
  8. **主快捷方式指向 `.cmd` 而不是 `.vbs`**：`.cmd` 不依赖 WSH、不依赖网址关联，
     而且出错时原因直接显示在屏幕上。静默需求由另一个「(静默)」快捷方式满足。
     代价明说：多一个控制台窗口。
  9. 创建快捷方式时顺手 `Unblock-File` 去掉「来自 Internet 的文件」标记（Mark of the Web），
     否则双击时会先弹「打开文件 - 安全警告」，看起来就像启动器坏了。

## 待决策（未来）

- **延期提醒的呈现方式**：桌面通知 / 日历标记 / 只在打开时提示？需要你用过之后决定。
- **补番计划的粒度**：按「每天 N 集」还是按「每周几看」还是两者都要？
- **是否接入 Bangumi API**（需要代理）：它的增益是更准的分集数、制作公司、类型标签。
- **假重复怎么合**：实测同一部番会落成两条记录（见 README「下一步」第 5 条）。
  让「标题包含关系」参与聚类能修掉它，但**必须防误合** ——
  实测「薬屋のひとりごと 亡妃の秘宝」与「薬屋のひとりごと」是两部不同作品。
  这需要你确认「宁可漏合还是宁可误合」，因为两种错误的表现完全不同：
  漏合 = 官方译名可能落在另一条记录上；误合 = 两部番被并成一部，数据混在一起。
- **机翻名要不要允许手动改**：目前只能靠官方名覆盖。若机翻错得离谱（如「马森楚」），
  手动改成你习惯的叫法会更好用，但需要一个新的「manual」出处优先级。
