## 二、项目是什么

当季新番自动汇总 + 追番管理 + 更新日历 + 补番库。**本地优先、单机使用、数据在自己手里。**

- 数据存本地 SQLite（`data/anime.db`），不依赖在线账号，没有云同步。
- 抓取三个源并做**字段级融合**：bangumi-data（中文名/放送时刻）、yuc.wiki（人工校对）、
  AniList（每集精确 UTC 时刻）。
- **过去季度不抓逐集放送时刻**（第八轮）：番已播完，`episode` 行没有使用场景；只抓清单、
  首播时刻与放送日历归属。当季与未来季度照旧抓逐集时刻。
- 缺中文名时用 Bing 机翻兜底，标成「临时机翻」，官方译名一到自动替换。
- 界面是 `web/` 下的原生 ES 模块 SPA，四个导航视图：周视图 / 全季总览 / 我的追番 / 变更。
  搜索视图的代码还在（`renderSearch`），但导航入口已按用户要求去掉，加番用 `pnpm add`。

**最容易做错的一件事**：日本电视台把深夜番写成「日曜 24:30」——
放送日历上是**周日**，真实钟点是**周一 00:30**。数据库里同时保存两种归属
（`broadcast_weekday_jst` 与字面 `broadcast_time_jst`），日历提供两种口径切换。
任何涉及「这一集算哪天」的改动都要极其小心（见第四节第 1 条）。

## 三、怎么跑、怎么验

```powershell
pnpm install                        # 依赖只有 zod / undici / typescript / @types/node
node src/server/server.ts           # http://127.0.0.1:8787
pnpm exec tsc --noEmit
pnpm verify                         # 离线、用 :memory: 库
pnpm verify:api                     # 需服务已启动；会写真实库（先自动备份）
pnpm ui:smoke                       # 前端交互（需要服务）
pnpm preview:ui                     # 生成 data/_preview/preview{,-dark}.html
node src/server/cli.ts              # 不带参数会打印全部 CLI 命令
```

常用 CLI：`season` / `sync` / `update` / `translate` / `search` / `add` / `list` /
`week` / `changes` / `backups` / `reset` / `archive` / `stats` / `runs` / `audit`。
`update` 支持 `--seasons=2026-10,2024-10`（自己挑季度，可含库里没有的），优先于 `--backfill`。
`--incremental` 才跳过「上次真抓过」的季度；不给就按你挑的全抓。`--force` 是"连真抓过的也重抓"。
`--no-translate` 只抓清单（最快）；`--concurrency=4` 调机翻并发。
`audit` 是**只读**的季度体检（每季库内几部、首播真的在本季几部、上次真抓是什么时候），
排查「某个季度怎么更新都不增加」先跑它。

**HTTP 接口**（路由在 `src/server/server.ts` 的一个大 `if` 链里，没有框架）：
`/api/health` · `/api/overview` · `/api/week` · `GET|POST /api/my` · `PATCH|DELETE /api/my/:key` ·
`/api/override` · `/api/subject/:key` · `/api/search` · `/api/search/import` · `/api/sync` ·
`/api/update` · `/api/translate` · `/api/job` · `/api/job/cancel` · `/api/changes` ·
`/api/changes/ack` · `/api/ics` · `/api/export` · `/api/runs`。

`POST /api/update` 的范围参数：`seasons=2026-10,2024-10`（显式列表，优先于 `backfill`，
可含库里没有的老季度）、`backfill=N`（含当季，最小 1）、`incremental=1`（跳过上次真抓过的季度）、
`force=1`、`translate=0`、`heal=1`；响应里的 `scope` 说明这次到底抓了哪几季
（`backfillIgnored` 会明说参数被忽略），`summary.added` / 每季的 `added` 是**新增**部数
（`written` 只是 UPSERT 次数，不等于新增）。

`async=1` 让 `/api/update` 与 `/api/translate` **立刻返回 202**（界面走这条），
之后轮询 `GET /api/job` 拿阶段与进度，`POST /api/job/cancel` 请求停止。
同一时刻只允许一个任务（409）。同步路径保留给 CLI 和 `verify-api`。

## 四、改代码前必须知道的坑（按踩坑代价排序）

1. **深夜番归属**：动 `core/time.ts` + `core/calendar.ts`，必须保住
   `resolveAiringSlot()` 与 `toLiteralJstTime()` **互为逆运算**（有自检）。
2. **季度归属只有一份实现**：`db.ts` 的 `deriveSeasonFromAirTimes`，规则是
   「**集数最小的那一集的放送时刻**」推出的季度。写入时 `resolveSeasonForWrite` 用它，
   写库后 `repairSeasonAssignments` 也用它，两者必须一致。不要用「落在哪个加宽窗口」或
   「谁最后写入」判；比较时刻先 `Date.parse` 转毫秒（ISO 字符串字典序 ≠ 时间序）。
3. **多源融合优先级**：`core/merge.ts` 的 `FIELD_PRIORITY`。改它会静默改变所有数据的来源。
4. **延期检测的防假警**：`server/changes.ts` 的两条过滤（源优先级、最小时间差）不能删。
   有一条接口测试：连续两次同步，第二次必须产生 0 条变更。
5. **`.ics` 折行**：RFC 5545 要求每行 ≤ 75 **字节**且按 UTF-8 字节切，不要用字符数。
6. **机翻名出处 `title_cn_source`**：`db.ts` 的 `subjectValues` 必须让出处跟着
   「这次到底有没有给出官方中文名」走（官方写 `official`，没有写 `NULL`，靠 COALESCE 保住旧值）。
   曾经照抄 schema 默认值，一次同步把 34 条机翻名洗成了 official。
7. **备份必须处理 WAL**：先 `PRAGMA wal_checkpoint(TRUNCATE)`，再拷 `anime.db`，
   并把 `-wal`/`-shm` 一起拷。只拷主文件曾导致 `my_anime` 整表丢失。
8. **前端点击委托**：
   - `SELF_HANDLED` 排除自己绑过监听的按钮，否则点一次跑两遍。
   - 不要再加 `if (target.closest('#filter-panel')) return;`（第五轮把筛选块折进面板后，
     这句会让面板里所有按钮失效）。
   - **双击复制的单击拦截必须在取 `target` 之前**：
     `if (event.target.closest?.('[data-copy-title]')) return;`
     否则单击标题会先打开详情，双击的第二下落在遮罩上，复制永远不生效。
9. **`web/styles.css`**：
   - 组件里不写死颜色，全部走令牌；深色令牌写在两处（`@media` 与 `.theme-dark`），改要同步。
   - 每行几部用 `.per-row-N` 字面整数；`repeat()` 首参不能写 `min()/calc()/var()`，
     否则整条声明被浏览器丢弃、列表塌成单列。
10. **`desktop/` 与 `scripts/` 脚本纯 ASCII**：中文用 Unicode 码点拼（PS1 用 `[char]`，
    VBS 用 `ChrW`）。`.cmd` 里不要在 `if (...)`/`for (...)` 内用 `%ProgramFiles(x86)%`
    （右括号会提前闭合代码块，用 `%ProgramW6432%`）；块内改完要立刻读变量用
    `call :label` / `enabledelayedexpansion`。
11. **离线预览与前端测试的锚点**：`scripts/preview-ui.ts` 依赖
    `const WEEKDAYS` 与 `// 视图：我的追番 / 补番库` 两个锚点；动 `web/app.js` 段落结构要同步。
    `scripts/ui-smoke.ts` 的元素壳有四个坑（querySelector 连根匹配、querySelectorAll 递归、
    `open` 空串语义、重绘后旧节点脱离文档），改壳前先读脚本头注释。
12. **「这季抓过没有」只能看 `season_state`，不能数条目**（第八轮修的 bug，代价极高）：
    抓 A 季会按条目自己的放送时刻把几条写进相邻季度（bangumi-data 的窗口是季首前 20 天
    到季末后 20 天）。所以「库里已有 ≥1 部」根本不是抓过的证据 —— 用它当增量判据，
    那些季度会被永久跳过，表现就是「一个季度只有 10 部，怎么更新都不增加」。
    判据函数是 `sync.ts` 的 `seasonFetchDecision()`，状态表是 `db.ts` 的 `recordSeasonFetch()`。
    显式勾选的季度默认**不**增量（勾了就该抓），只有隐式 `backfill=N` 默认增量。
13. **过去季度不抓逐集放送时刻**（用户明确要求）：`time.ts` 的 `seasonIsPast()` 为真时，
    `fetchSeason()` 传 `schedules: false`，AniList 换成不带 `airingSchedule` 的查询、
    bangumi-data / yuc 不产出分集。⚠ 由此必须守一条：`syncSeason` 在
    `outcome.schedules === false` 时**不做 `detectChanges()`** ——
    "这次没抓分集"不等于"分集消失了"，否则一次古早季度回填会刷出几千条假的
    `episode-removed`（`changes.ts` 头注释里那类假报警）。首播时刻与
    `broadcast_weekday_jst / time_jst` **仍然要抓**：季度归属与总览排序靠它。
14. **机翻的限速语义**（第九轮提速的核心，改回旧写法会立刻慢 6 倍）：
    `mt.ts` 的 `translateTitle` **不能**改成「每条开头先 sleep」—— 那会让每条多等 700ms，
    实测 1.92 秒/条。正确做法是 `takeRequestSlot(minIntervalMs)`：只有「距上次请求不足间隔」
    才等，而且取号**必须串行化**（并发时几个 worker 会同时算出同一个出发时刻，限速就废了）。
    并发默认 4（`DEFAULT_TRANSLATE_CONCURRENCY`），失败只做串行重试，不放大风控。
15. **`Promise.allSettled` 抓三源时 `reports` 的顺序**：`providers` 数组与 `settled` 下标一一对应，
    失败的第 i 项必须用 `PROVIDERS[i]` 取名字 —— 别用「成功项的下标」去索引 provider（会错位）。
16. **长任务的进度只能靠 `onProgress` 回调，不能靠日志**：`server.ts` 的 `beginJob()` 把
    `onProgress / onTranslateProgress / onSeasonDone` 收进任务快照，前端轮询 `/api/job`。
    新增阶段时记得同时喂 `snapshot.stage` 与 `message`，否则界面会停在上一句话。

## 六、数据安全（追番列表是资产）

- **自动备份**：启动服务时、以及每次写库（同步 / 更新）**之前**备份到 `data/backups/`，
  只保留最近 20 份。`node src/server/cli.ts backups` 可看。
- **导出**：界面「导出我的数据」→ `GET /api/export`，含追番、进度、手动修正、变更历史。
  抓来的番剧数据可重新抓，不在导出里。
- **不可重建的数据**：`my_anime`、`schedule_override`、`change_log`。改 schema 必须写迁移
  （参考 `db.ts` 的 `ensureColumn`，幂等）。
- ⚠ `verify:api` **会写真实库**：它会加两条测试追番（一条 tracking、一条 backlog）、
  改一条进度、跑一次全量机翻与全季更新，并产生一批待处理变更。
  **跑完要清干净**（不要给 `verify:api.ts` 加自动清理逻辑，它区分不了用户数据）：
  1. `GET /api/my` 找出今天由自检新增的两条（通常是 `anilist:*` 补番库 + `bgm:*` 追番中，
     `added_at` 与运行时间吻合），`DELETE /api/my/:key` 删掉；
  2. `POST /api/changes/ack`（body `{}`）把这一轮产生的待处理变更标记已读；
  3. 用 `GET /api/health` 确认 `tracking / backlog / pendingChanges` 回到运行前的数字。
  实测清理后：`tracking 8 / backlog 24 / pendingChanges 0`。

## 七、环境与网络（本机实测，别重复踩）

## 八、已知失败 / 待办

**当前已知失败（不是本轮回归）**：

1. `verify:api` 的「连续两次同步，第二次不产生变更」：第二次仍报十几条
   `episode-removed`。根因是当前源站返回的分集比库里少，属于源站波动。
2. `verify:api` 的「`POST /api/update` 全流程」：`backfill=1` 时测试期望
   `archive.seasons` 有 1 条，但 `runFullUpdate()` 刻意把主季从回填列表排除，实际是 0 条
   （`src/server/sync.ts` 的 `mainSeason` 过滤）。测试断言与实现不一致，改一处即可；
   暂时不要为了让它变绿去改抓取逻辑。

**已知取舍（第八轮，不是 bug）**：过去季度不抓逐集时刻 → 上一季（如 10 月时的 7 月）
也按"过去"处理，所以它的延期 / 改档不会再被检测到。已入库的分集时刻不会丢，只是不更新。
如果哪天要恢复，把 `fetchSeason()` 里的 `seasonIsPast()` 换成"再宽一季"即可，一处改动。

**待办（按建议优先级）**：

1. **假重复合并**（唯一已知未修）：同一部番落成两条记录（标题归一化不相等、两条都无跨源 ID）。
   不能草率用「标题包含关系」合（`薬屋` 剧场版与 TV 是两部作品）。先做只报告不修改的
   `cli.ts dedupe`，让用户定「宁可漏合还是宁可误合」。
2. **Bilibili PGC Provider**：把「国内几点能看」落到每集 `pub_at_utc`（timeline 的 `pub_ts` 已验证可用）。
3. **桌面通知**：更新前提醒；`.ics` 已覆盖手机端。
4. **补番计划的界面入口**：数据层已支持 `planned_weekday_jst` / `planned_eps_per_day`，界面未做。
5. **Bangumi API（需代理）**：增益是更准的分集数与制作公司。

**明确不做**：在线播放 / 弹幕、社交、云同步账号、Bangumi OAuth、独立手机 App。

## 九、桌面端

- 双击 `desktop\创建桌面快捷方式.cmd`（一次），桌面出现三个快捷方式：主程序（`.cmd`，可见控制台）、
  静默版（`.vbs`，日志 `data\launcher.log`）、停止。

  启动器直接调用浏览器 exe（按 `UserChoice` → Chrome → Edge → Firefox 查找）。
