## 二、这个项目是什么

当季新番自动汇总 + 追番管理 + 更新日历 + 补番库。**本地优先、单机使用、数据在自己手里。**

- 数据存本地 SQLite（`data/anime.db`），不依赖任何在线账号，没有云同步。
- 抓取三个源并做**字段级融合**：bangumi-data（中文名/放送时刻）、yuc.wiki（人工校对）、
  AniList（每集精确 UTC 时刻）。
- 缺中文名时用 Bing 机翻兜底，标成「临时机翻」，官方译名一到自动替换。
- 界面是 `web/` 下的原生 ES 模块 SPA，五个视图：周视图 / 全季总览 / 我的追番 / 变更 / 搜索加番。

**这个项目最容易做错的一件事**：日本电视台把深夜番写成「日曜 24:30」——
放送日历上是**周日**，真实钟点却是**周一 00:30**。同一集两种口径落在不同的一天甚至不同的一周。
本项目的处理：数据库里**同时**保存两个星期归属，日历提供两种分组口径由用户切换，
所有时刻统一以 ISO8601 UTC 存储。**任何涉及"这一集算哪天"的改动都要极其小心**（见第五节）。

`POST /api/update` 的范围参数（都可省略）：

- `season=2026-10` —— 主季，默认当季；给了 `seasons` 时主季 = 列表的第一个
- `seasons=2026-10,2024-10` —— **自己挑要抓哪些季度**（按给定顺序、跳过中间季度、
  可以是库里没有的老季度）；给了它就以它为准，`backfill` 被忽略（响应里的
  `scope.backfillIgnored` 会说，界面也会显示，不静默）
- `backfill=3` —— 当季 + 往回数几季（含当季，**最小 1**：0 等同于只抓当季）
- `force=1` —— 已有数据的季度也重抓；`translate=0` / `limit=N` / `heal=1` 同前

响应里新增 `scope`（`{ mode, seasons, backfill, backfillIgnored, force, translateSeasons }`），
界面就是靠它说清"这次到底抓了哪几季"以及"机翻覆盖了哪几季"。

### ⚠ 自检脚本会动真实数据

`scripts/verify-api.ts` 打的是**真实服务**，所以它会往 `data/anime.db` 里写东西：
把一部深夜番加进追番、把进度改成 2、导入一部远程搜索到的番。
`scripts/verify.ts` 用 `:memory:` 库，**不碰**真实数据。

这意味着**用户正在用的库会被自检污染**。要知道的事：
- 跑自检前先 `node src/server/cli.ts backups`（其实每次写库前都会自动备份），
  想回退就从 `data/backups/` 里挑一份。
- 如果你想让自检完全不动真实库，跑之前把库挪走（`data/anime.db` → 临时改名），
  跑完再挪回来 —— 但那样 `verify-api.ts` 里的断言是在空库上跑的，意义会小很多。
- **不要**为了"让自检更干净"而给 `verify-api.ts` 加"清理自己写入的数据"的逻辑：
  它清除时可能误删用户真实添加的条目（区分不了）。当前取舍是**宁可脏一点也不要误删**。

## 五、改代码前必须知道的坑（按踩坑代价排序）

1. **深夜番归属**。任何涉及"这一集算哪天"的改动都要动 `core/time.ts` + `core/calendar.ts`，
   并且必须保住 `resolveAiringSlot()` 与 `toLiteralJstTime()` **互为逆运算**（有自检）。
2. **季度归属的判据只有一份实现**：`db.ts` 的 `deriveSeasonFromAirTimes`，
   规则是「**集数最小的那一集的放送时刻**」推出的季度。
   写入时 `resolveSeasonForWrite` 用它，写库后 `repairSeasonAssignments` 也用，
   **所以两者必然一致、幂等**。改其中一处必须同时改另一处，否则会互相打架并刷出假变更。
   - 不能用"落在哪个加宽窗口"判：2026-07 加宽 7 天后覆盖到 10-07，会把 10 月新番判给 7 月。
   - 不能用"谁最后写入"判：回填旧季会把当季条目偷走（实测当季从 123 部掉到 56 部）。
   - ⚠ 比较时刻**先 `Date.parse` 转毫秒**：ISO 字符串的字典序不等于时间顺序
     （`'2026-10-03…' < '2026-09-25…'` 为 true）。
3. **多源融合的字段优先级**（`core/merge.ts` 的 `FIELD_PRIORITY`）。
   改优先级会静默改变所有数据的来源，必须核对覆盖率分布。
4. **延期检测的防假警**（`server/changes.ts`）。那两条过滤（源优先级、最小时间差）不能删。
   有一条接口级测试：**连续两次同步，第二次必须产生 0 条变更**。
5. **`.ics` 导出的折行**：RFC 5545 要求每行 ≤ 75 **字节**且按 UTF-8 字节切，不要用字符数。
6. **机翻名的出处 `title_cn_source`** 是「临时译名」能标出来、能被官方名替换的唯一依据。
   `db.ts` 的 `subjectValues` 必须让出处跟着「这次到底有没有给出官方中文名」走：
   给出了写 `'official'`，没给出写 `NULL`（靠 `PRESERVE_WHEN_EMPTY` 的 COALESCE 保住旧值）。
   曾经直接照抄 `subject.titleCnSource`（schema 默认 `'official'`），一次普通同步就把
   34 条机翻名洗成了 official。
7. **备份必须处理 WAL**：先 `PRAGMA wal_checkpoint(TRUNCATE)`，再拷 `anime.db`，
   并把 `-wal`/`-shm` 一起拷。实测只拷主文件时 `subject` 126 行而 `my_anime` **0 行**
   —— 追番列表整条丢。
8. **前端按钮不要既绑 `addEventListener` 又被 document 事件委托处理**，
   否则点一次跑两遍（「更新数据」跑两遍＝两倍源站请求与机翻额度）。
   现有做法：`web/app.js` 里 `SELF_HANDLED` 集合排除自己绑定过的按钮。
9. **`desktop/` 与 `scripts/` 脚本必须纯 ASCII**，中文用 Unicode 码点拼（PS1 用 `[char]`，
   VBS 用 `ChrW`）。另外两个 `.cmd` 陷阱：**不要**在 `if (...)`/`for (...)` 里用
   `%ProgramFiles(x86)%`（右括号会提前闭合代码块，用 `%ProgramW6432%`）；
   想在块内改并立刻读变量要用 `call :label` 或 `enabledelayedexpansion`。

## 五之二、第五轮 UI 改造（已完成，全绿）

五条都是界面需求，**没碰**深夜番归属、融合字段优先级、延期检测、`.ics` 折行这四处危险区。
改动只在 `web/`（index.html 没动）、`src/server/db.ts`、`src/server/server.ts`、`scripts/verify-api.ts`。

### 1. 周视图调序

「接下来要更新的」倒计时列表原来压在周格子上面，现在挪到**周格子下面**
（用户主要看的就是那排「周一~周日」）。只改了 `renderWeek()` 里模板的先后顺序。

### 2. 四张分布图 → 搜索栏右边的「筛选 / 排序」面板

原来的 `按放送星期分布 / 按国内平台分布 / 按类型标签分布 / 按媒体类型` 四张卡片
**整块删掉**（太占地方），改成按需展开的面板，各部分数写在筛选项旁边。

- 位置：`#filter-toggle` 按钮在搜索框右边；`state.filtersOpen` 记住展开状态（localStorage）。
- 面板三小组：快速筛选（我追的/补番库/放送中/未开播/B站有版权/缺中文名）、
  排序方式、每行几部；下面四栏：放送星期、媒体类型、类型标签、国内平台。
- **草稿式计数**：选项旁的部数一律以「搜索框 + 快速筛选」的结果为基数，不随面板内其他选择变化
  ——点一个筛选数字就全变会越看越糊。要的是稳定可读，不是精确的 faceted count。
- 逻辑：**同一栏选多个 = 取并集；不同栏之间 = 取交集**。已选条件渲染成可单删的 chip
  （`#active-filters`），面板收起时也看得见，否则「怎么列表只剩 3 部」会变成未解之谜。
- ⚠ 点击委托里有一句 `if (target.closest('#filter-panel')) return;`：
  面板内部的交互自己处理，**必须**保住这句，否则点面板里的东西会被委托当成别的按钮。
- ⚠ `renderSeason()` 末尾会调 `renderFilterPanelOnly()` 重新绑四个 `<select>` 的 change。
  原因是 `select` **不触发 click**，走不了点击委托；不重绑就会出现「下拉框没反应」。

### 3. 类型标签中文化（只做显示映射）

`web/app.js` 顶部 `GENRE_CN` 把 AniList 的英文标签译成中文（Action→动作、Slice of Life→日常…），
`genreLabel()` 没有映射时原样返回（yuc.wiki 来的「机战/转生」本来就是中文）。
卡片上加了 `title="原始标签：Action"`，鼠标悬停能看到原文。

**为什么不在抓取/落库时翻**：`genre` 是融合字段，写中文进去会和「字段优先级」较劲、
下次同步还会被英文覆盖（见第五节第 3 条）。显示层翻译是零风险的。
`MEDIA_TYPE_CN` 同理（TV→TV 动画、MOVIE→剧场版）。

### 4. 每行几部（3~7 可调，记在 localStorage）

`perRowStyle()` 返回 `--per-row-w: calc((100% - (n-1)*10px) / n)`，
`.subject-list` 用 `auto-fill + minmax(min(100%, var(--per-row-w)), 1fr)`。
刻意**不写死 N 列**：**全局**宽度会横向溢出、手机上尤其明显。
窗口变窄时由媒体查询降列（那两条 `!important` 是用来压掉元素上行内 `--per-row-w` 的，别删）。

### 5. 季度多选 + 列表排序

- `season` 参数支持逗号多季：`/api/overview?season=2026-10,2026-07&sort=firstAir`。
  服务端 `resolveSeasons()` 去重、丢弃非法项并**回给界面提示**（不静默回落成当季——
  那样"勾了两季其中一季打错字"会静默变成只查当季，很难发现）。
- 单季行为完全不变（`season` 就是单值），`verify-api.ts` 的既有断言不受影响。
- 周视图 / `.ics` 是**单季**口径，用**主季 = 第一个选中的季度**；多选时界面会写明这一点。
- `state.selectedSeasons` 不允许清空（至少留一季），空集合会让请求回落当季、和界面显示对不上。
- 排序（`db.ts` 的 `SEASON_SORT_SQL` 白名单 + `resolveSeasonSort()`）：
  `firstAir`（默认，早→晚）/ `firstAirDesc` / `weekday` / `titleCn` / `totalEps`。
  排序在**服务端 SQL 里做**，不在前端排（列表最多 500 多部，且要保持与分页/统计同源）。
  因此前端换排序/多季时必须**重新拉数据**（`changeSort()` / `applySeasonChange()` 都走
  `loadOverview()`），不能只重排手上那个数组。
  `SEASON_SORT_SQL` 是白名单：**绝不**把调用方传进来的字符串直接拼进 SQL。
- ⚠ **`listSeasonSubjects` 的默认排序从"按放送星期"改成了"按首集放送时间"**。
  这就是踩到的那个坑，见下。

### 这一轮真实踩到的坑：`verify-api.ts` 的选择器缺陷

改完默认排序，`node scripts/verify-api.ts` 从 28/28 变成 **27/28**，失败项是
`POST /api/translate 不会覆盖已有的官方中文名`。查下来不是数据被改坏，而是**测试自己写错了**：

- 它挑"官方名"用 `before.subjects.find(s => s.titleCn)` —— 只保证"有中文名"，
  而中文名**可能是上一轮机翻的**（`title_cn_source = 'machine'`，2026-10 里有 30 多条）。
  随后第 594 行却断言 `titleCnSource === 'official'`，撞上机翻名必然失败。
- 旧排序（按放送星期）下第一个有中文名的恰好是 `title:タヌキとキツネ`（official）所以一直没暴露；
  新排序（按首集放送时间）下第一个是 `anilist:213298 松松的图鉴`（machine）→ 炸。
- **修法是改检查，不是改回排序**：`find(s => s.titleCn && s.titleCnSource === 'official')`。
  验数据也确认了库是好的：有中文名的条目里**没有**一处出处是 NULL，即数据本身没被写坏。

**下一轮注意**：`verify-api.ts` 会往**用户正在用的库**里写东西（见第四节）。它跑一次
`limit=0` 的全量机翻、`/api/update` 一次全季重写。要复现"干净"的结果，先把
`data/anime.db` 拷一份再跑，别拿真实库反复试。另外 `web/` 是静态文件、改完刷新即可生效，
但**改了 `src/` 必须重启服务**才生效（前端此时会优雅退回单季，不会崩）。

## 五之三、第六轮：全局 UI 美化（已完成，全绿）

`web/index.html`（顶栏收纳）、`web/app.js`（内联样式换成 class + 菜单交互）。

### 设计基准

- **两套主题，跟随系统**（`prefers-color-scheme`），页面上**没有**手动切换开关。
  浅色是干净的白底卡片，深色是带蓝紫倾向的深底 + 更亮的卡片。
- **一处渐变**：青绿→蓝→紫（`--grad`），只出现在主按钮、今天那一列的表头、选中的筛选项、
  进度条、统计卡顶线、品牌图标。其余全是中性色 —— 规则是「让海报和标题跳出来，其它退到背景里」。
- 顶栏与标签页 `sticky` + 背景模糊；卡片统一 `--radius` 11px、浅投影，hover 抬 2px。

### 令牌结构（改样式前先看这段）

```
:root                      ← 浅色令牌（默认），含字体/字号/圆角/间距/渐变
@media (prefers-color-scheme: dark) { :root, :root .theme-dark { ... } }
:root.theme-dark, .theme-dark { ... }   ← 强制深色（与系统偏好无关）
```

- ⚠ **组件里绝不要写死颜色**。全部走令牌，否则浅色主题下会出现
  「深色卡片浮在白底上」这种一半一半的效果。当前 `styles.css` 里
  除令牌定义外**零**个硬编码色值（可用 `#[0-9a-fA-F]{3,6}` 反查）。
- 深色令牌写了两处（`@media` 里一处、`.theme-dark` 一处）。第二处是为了能**强制**某个区域
  用深色 —— 离线预览页靠它把浅色与深色放进同一张图里对比。**改深色时两处都要改**
  （深色 31 个令牌，浅色独有 18 个是字体/字号/圆角这类与主题无关的）。
- `.theme-dark` 用的是 `:root.theme-dark, .theme-dark` 两段选择器：前者给 `<html>` 加类时用，
  后者给任意容器加类时用（`body` 的背景与文字色因此也能被正确覆盖）。

### 顶栏收纳（功能全保留）

原来是 5 个按钮 + 2 个下拉挤成一排，窄窗口会折成两三层。现在：

- ⚠ `closeMoreMenu()` 里的「点别处收起菜单」必须留着：`<details>` 自己管开合，
  **不会**在点空白处自动关，不补这个菜单会一直挂着挡住内容。
- ⚠ `SELF_HANDLED` 那套机制没变：`sync-btn` / `translate-btn` 仍然自己绑监听，
  移动位置不影响「点一次只跑一次」。
- Esc 的优先级：先收菜单，菜单没开才关详情弹窗。

## 五之四、第六轮之后的真实 bug 修复（用户实测反馈）

第六轮"美化"上线后用户实测报了四件事，其中**第一件是真 bug，而且相当严重**。

### 1. 🔴 筛选面板里所有按钮全部失效（已修）

**症状**：整个「筛选 / 排序」面板里，点任何一个筛选块、每行几部、排序 —— **都不变色也不生效**；
只有面板上方那四个 `<select>` 下拉能用。用户原话是"按了也不变色也不生效"。

**根因**：点击委托里有一句

```js
if (target.closest('#filter-panel')) return;   // ← 元凶
```

这句是**第五轮之前**的写法：那时可点选的分布条在面板**外面**，委托只该处理面板外的元素。
第五轮把筛选块折进面板之后，`data-toggle-filter` / `data-quick-filter` / `data-per-row` /
`data-sort` 这四类按钮**全都在面板里**，于是这句把它们的点击**全部提前 return 掉**。
四个 `<select>` 照样能用，是因为它们走 `change` 事件、不经过点击委托 ——
所以症状看起来像是"只有下拉能用"，非常具有迷惑性。

**修法**：删掉那一句（面板内部本来就该由点击委托统一处理）。已在注释里写明**不要加回来**。

**为什么之前没发现**：`pnpm ui:smoke` 当时还不存在；而离线预览页只能证明静态样式。
更早那个"哑元素壳"式冒烟测试里 `closest()` 恒返回 `null`，恰好把这个环节屏蔽掉了
—— 也就是说**旧测试结构性地无法发现这类 bug**。这正是 `ui-smoke.ts` 要留下来的原因。

### 2. 四栏分面默认折叠（用户要求）

原来是四栏全铺开（类型标签 30 多项），面板被顶得很长。现在改成 `<details>` 折叠：
默认只显示**标题 + 「N 项」/「已选 M」+ 已选摘要**，点标题才展开。

- 用 `<details>` 而不是自己写开合：原生支持键盘（Tab + Enter），且 `summary` 不是 `button`，
  点击委托不会命中它，不会互相干扰。
- **展开状态要记住**：面板每点一次都会整块换节点，不记的话用户展开一栏、点一下又被收起。
  做法是在 `document` 上**委托监听 `toggle` 事件**（会比绑到每个 `<details>` 更耐重绘），
  状态存 `state.facetsOpen`。
- 有选中项的栏会强制展开（这样刷新后能立刻看到自己筛了什么）。

### 3. 卡片补上「详情」按钮（用户要求）

未加入列表的卡片原来只有「追番 / 补番」两个按钮 —— 用户说"我总要了解之后再选择追或者补番吧"。
现在**未加入列表的卡片也是三个按钮：详情 / 追番 / 补番**，且「详情」排在前面。
已在列表的卡片保持「详情 / 移除」不变。

### 4. 海报偶尔变黑（已加兜底）

原因：封面来自远程 CDN，偶发加载失败（限流 / 抖动 / 图被删），失败时 `<img>` 会留下
空白或**纯黑**的框。现在 `coverHtml()` 给 `<img>` 加了 `onerror`：加载失败就把自己换成占位块
（`ep-cover-ph` + `◈`），至少形状和颜色协调，不会突兀地黑一块。
`--cover-bg` 也保证了加载期间不是纯黑。

⚠ 这只是兜底。**如果用户还看到黑块，那说明失败发生在别处**（比如图片解码失败但没触发 `error`），
届时要让他打开 DevTools 的 Console / Network 看具体是哪张图、什么状态码。

### 这一节的经验（给下一轮）

- **"按钮点了没反应"优先怀疑点击委托的提前 return**，而不是先怀疑渲染。
  在委托函数入口打印一次 `event.target` 就能定位。
- 写前端冒烟测试时，**哑元素壳（`closest()` 恒 null）会系统性漏掉委托类 bug**，
  必须用会冒泡的真元素树。
- 用户能看到而我这边看不到的界面问题，**先要一张截图**（用户给了三张，一次就把范围缩到
  "面板内的按钮"），比自己反复读代码快得多。

## 七、桌面端（已修好并确认可用）

**用法**：双击 `desktop\创建桌面快捷方式.cmd`（一次），桌面会出现三个快捷方式：
「新番追番日历」（主，`.cmd`，可见控制台）、「新番追番日历(静默)」（`.vbs`，

**两个真实踩过的坑（已在启动器里绕开，别改回去）**：

1. **不依赖 http 网址关联**。本机 `HKCU\...\UrlAssociations\http\UserChoice` = `QuarkHTM`，

   浏览器并直接启动（exe 不存在就跳过），再依次尝试 Chrome → Edge → Firefox 的常见路径。
   **不要**把它改回 `shell.Run url` 或 `start "" "http://..."`。
2. **创建快捷方式时 `Unblock-File`** 去掉「来自 Internet 的文件」标记（Mark of the Web），
   否则双击会先弹「打开文件 - 安全警告」，看起来像启动器坏了。
3. 主快捷方式指向 `.cmd` 是刻意的：不依赖 WSH（`.vbs` 可能被安全软件拦）、

## 九、待办 / 已知未做（按建议优先级）

1. **假重复的合并**（唯一"已知未修"）。
   实测同一部番会落成两条记录，例如 `anilist:210482` 与

   误合 = 两部番数据混在一起，更难发现更难恢复）。建议先做一个**只报告不修改**的
   `cli.ts dedupe`。
2. **Bilibili PGC Provider** —— 把「国内几点能看」落到每一集（`pub_at_utc`）。

4. **补番计划的界面入口** —— 数据层已支持（`planned_weekday_jst` / `planned_eps_per_day`），
   界面上还没做。
5. **Bangumi API（需代理）** —— 增益是更准的分集数与制作公司。
6. 仍未验证的部分见 `docs/sources.md` 第十一节。

**明确不做**：在线播放/弹幕、社交、云同步账号、Bangumi OAuth、独立手机 App。
